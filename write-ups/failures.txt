Failures and Challenges when using LLM Support for Checker Framework Issue #3211
======================================================================================

1. **Deep framework internals understanding**
   - LLM struggled with Checker Framework's type hierarchy initialization
   - The "Multiple bottoms found" error required understanding of internal framework logic
   - Documentation for handling multiple type hierarchy branches was not readily available
   - Framework's bottom type detection algorithm was not intuitive

2. **Type system complexity**
   - Initial assumption that BitPattern could be a direct subtype of UnknownSignedness was incorrect
   - The relationship between SignednessBottom and other qualifiers was complex
   - Understanding when a qualifier is automatically detected as a "bottom" was non-trivial
   - Required trial-and-error to understand the proper hierarchy structure

3. **Build and runtime discrepancies**
   - Code compiled successfully but failed at runtime in checker
   - JAR file updates didn't always reflect in checker/bin/javac script immediately
   - Caching issues made it hard to determine if changes were taking effect
   - Test framework errors masked the actual implementation problems

4. **Testing infrastructure complexity**
   - Original master branch already had failing tests (unrelated to changes)
   - Test framework initialization errors made it hard to isolate new bugs
   - Couldn't easily run individual test files in isolation
   - "Error when invoking constructor" messages were cryptic

5. **Limited access to issue details**
   - Could not directly access GitHub issue #3211 to see original requirements
   - Had to infer requirements entirely from test file
   - No access to issue comments or discussion that might provide context
   - Uncertain about edge cases or specific design decisions

6. **Java module system conflicts**
   - Encountered IllegalAccessError when trying to run checker directly
   - Had to work around Java module export restrictions
   - Direct javac invocation required special setup

7. **Initially incomplete solution - RESOLVED**
   - Initial approaches with BitPatternValue caused "Multiple bottoms" error
   - Eventually resolved by simplifying type hierarchy
   - Direct SignednessBottom → BitPattern inheritance worked
   - Solution required multiple iterations but was ultimately successful

8. **Framework-specific annotations**
   - Initially tried to use @Bottom annotation incorrectly
   - Wasn't clear which framework annotations were available
   - Had to search for correct annotation imports

9. **Time and iteration costs**
   - Each compile-test cycle took significant time
   - Multiple rebuilds required to ensure changes propagated
   - Trial-and-error approach consumed many tokens/iterations

10. **Documentation gaps**
    - Limited examples of adding new qualifiers to existing hierarchies
    - No clear guide for resolving bottom type conflicts
    - Would benefit from more examples of complex type hierarchy modifications

**Technical Issue Summary - RESOLVED:**
The "Multiple bottoms" issue was resolved by:
1. Removing the BitPatternValue intermediate type
2. Making SignednessBottom a direct subtype of both SignedPositive and BitPattern
3. The simpler hierarchy allowed the framework to correctly identify SignednessBottom as the sole bottom

**Final Solution Architecture:**
- Type Hierarchy: UnknownSignedness → BitPattern → SignednessBottom
- Stub File: SignednessChecker.astub declares Float/Double bit conversion methods
- TreeAnnotator: Preserves @BitPattern type through bitwise operations
- Visitor: Validates that @BitPattern is not used in arithmetic operations

**Final Test Results:**
✅ All 8 expected BitPattern errors correctly trigger (100% success rate)
✅ All allowedUses operations pass (0 false positives on valid code)
✅ Test runs successfully without framework crashes
